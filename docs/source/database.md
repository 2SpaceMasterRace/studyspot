# Postgres database

Postgres is StudySpot's serving database in every environment: a container locally, an RDS instance on AWS. The model, migrations, loader, and study-spot queries are implemented; the search projection is not.

One database everywhere is a deliberate narrowing. The previous implementation ran SQLite locally and a hosted libSQL database in deployment, behind one adapter and two drivers, and the cost of that arrangement was that local behaviour and deployed behaviour were only ever as similar as the adapter managed to make them. Postgres is cheap enough to run locally that the second implementation bought nothing.

## Environment model

| Environment | Database | `DATABASE_URL` |
|---|---|---|
| Docker Compose | The `postgres` service, on the `postgres-data` volume | `postgresql://studyspot:studyspot@postgres:5432/studyspot` |
| Native development | The same Compose service, published on `127.0.0.1:5432` | `postgresql://studyspot:studyspot@localhost:5432/studyspot` |
| AWS | RDS `db.t4g.micro` in private subnets | Generated by Terraform and passed to the Lambda functions |
| Vercel | None, unless the RDS instance is made publicly reachable | Not set |

The local credentials are `studyspot:studyspot` and are meant to be: the database listens on `127.0.0.1` only and holds a rebuildable copy of a public dataset. Deployed credentials are generated by Terraform, never written down here, and never shared between environments.

The Vercel row is empty on purpose. The RDS instance sits in private subnets with `database_publicly_accessible = false`, so nothing outside the VPC can reach it and the Vercel deployment serves the frontend and the liveness endpoint but has no database behind `/api/spots`. See [Deployment](deployment.md) for what that means in practice.

## Configuration

The application has exactly one database variable:

```text
DATABASE_URL
```

`dj_database_url.parse()` turns it into Django's `DATABASES` setting, so the same URL form works for a container, a laptop, and RDS. Two settings are applied on top of it, both in `src/backend/studyspot/settings.py`:

- **A connection per request**, through `conn_max_age=0`. Reusing a connection across requests is the usual advice for a long-lived server, and it is wrong here: AWS Lambda freezes an execution environment between invocations, and a connection held across the freeze is normally a dead socket by the time the next request thaws it. Reconnecting costs a handful of milliseconds; serving an error because a pooled socket expired costs a request.
- **A five-second connect timeout**, shorter than the API function's own timeout, so a database that is gone produces a `503 database_unavailable` response rather than a request that dies when Lambda stops it.

`DATABASE_SSL_REQUIRE=true` adds `sslmode=require`. Nothing reads a secret from a file, because two of the three environments have no filesystem to read one from.

An unreachable or unmigrated database is reported as a `503` with the `database_unavailable` code by `studyspot.middleware.DatabaseUnavailableMiddleware`, rather than as a stack trace. The driver's own message names the host and sometimes the failing statement, so it is logged and not returned.

## Schema and migrations

The schema is Django migrations, in `src/backend/spots/migrations/`. There is no hand-maintained `schema.sql` any more, and no separate step that creates tables at startup: a database is brought up to date with

```shell
just migrate
```

and a model change produces a migration with

```shell
just makemigrations
```

`just django-check` runs `manage.py makemigrations --check --dry-run`, which fails when the models and the migrations disagree. That check is part of `just check` and CI, so a model edit cannot reach `main` without the migration that implements it.

The `spots` table carries three check constraints — a known borough, a latitude in range, a longitude in range — because the loader writes in batches without calling `full_clean()` on every row, and the database should refuse a sixth borough whatever wrote it.

### Why no column declares a collation

Every text column uses the database's collation, including `id` and `name`, and that is deliberate rather than an omission.

`GET /spots` pages by `(name, id)`, and paging is only safe when that sort key is total: if two rows can compare equal, the database may order them differently between two queries, and a row that moves across the page boundary is served twice or not at all. The tiebreaker is what provides that, not the collation — `id` is a unique primary key, so two rows with the same name are still separated, under any deterministic collation. Which collation is in force changes what order the names come out in, never whether paging is stable. The published contract says the order does not move; it does not promise a particular order.

An earlier version of this schema pinned `id` and `name` to `"C"` to make the ordering byte-wise, on the theory that a locale collation could let two names tie. That theory was wrong, and the pin was actively harmful. Django compiles `icontains` and `iexact` to `UPPER(column) LIKE UPPER(%s)`, and `UPPER()` folds according to the collation of its argument: a `"C"`-collated column folds ASCII only, while the bound parameter folds under the database collation, so the two sides disagreed on every non-ASCII letter. `UPPER('café')` was `'CAFÉ'` for the parameter and `'CAFé'` for the column, and `name__iexact='Café Grumpy'` could not match the row it was copied from. NYC Open Data is full of accented names.

Leaving both columns on the database collation makes the two sides fold identically, which is the property that matters. It is correct whether the cluster was initialised with `en_US.UTF-8` or with `C`.

### Why there are no case-folded companion columns

The previous schema stored a `_folded` copy of every filterable column, holding Python `str.casefold()` output, because SQLite's own `lower()` and `LIKE` only fold the ASCII range. Postgres folds in the database instead: Django's `iexact` compiles to `UPPER(column) = UPPER(%s)` and its `icontains` to `UPPER(column) LIKE UPPER(%s)`, so there is nothing to maintain alongside the real column — provided every column involved uses the database collation, which is the subject of the section above. What replaced the extra columns is three expression indexes — `UPPER(neighborhood)`, `UPPER(borough)`, `UPPER(university)` — because a filter on `UPPER(column)` can only use an index on the same expression.

One behavioural difference survives the retirement of those columns: `str.casefold()` maps `ß` to `ss` and Postgres `UPPER()` does not, so a search for "strasse" no longer matches "Straße". No record in the NYC snapshots is affected.

## Data lifecycle

```text
NYC Open Data -> data/ingest.py -> data/spots.json -> load_spots -> spots table
                                                                 \-> search projection
```

`data/spots.json` is the reproducible normalized snapshot and the source of truth. The `spots` table is a rebuildable projection of it, and any Meilisearch index is another projection, not an independent source of truth.

Load or reload the local database with:

```shell
just load-data
```

The `load_spots` management command validates every record against the model before anything is written, then replaces the table's contents in one transaction, so the serving table can only ever hold records the API can serve and a snapshot that fails validation halfway leaves the previous contents in place. It replaces rather than upserts, because a record dropped upstream has to disappear here too. It is safe to re-run. Pass `--dataset` to load a different snapshot.

On AWS the same command runs inside a Lambda function:

```shell
just aws-migrate
just aws-load
```

Neither step can run from a laptop, because the database has no public endpoint. The loader prefers the copy of `spots.json` bundled into the deployment package, and falls back to the one in the repository.

Normal Compose shutdown preserves the `postgres-data` volume; `just clean` deletes it. That is safe while every record can be rebuilt from `spots.json`. If StudySpot later stores favorites, corrections, accounts, or import cursors, backups and backward-compatible migrations become release requirements.
